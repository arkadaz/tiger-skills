Format rules (Keep a Changelog 1.1.0). Changelogs are for humans, not machines. [Unreleased] always sits at the top; below it, latest release first, every release headed [VERSION] - YYYY-MM-DD (ISO 8601, date always shown). Each release carries TWO audience bands: User-facing changes (benefit-phrased — what the user can now do, no jargon) and Internal changes (technical — APIs, schemas, migrations, dev environment). Inside each band, group entries under exactly these category names: Added (new features), Changed (changes in existing functionality), Deprecated (soon-to-be removed), Removed (now removed), Fixed (bug fixes), Security (vulnerabilities) — and omit empty categories. An entry for every version; same change types grouped together.

Written by: update-docs ONLY, at each feature close-out (one entry per passing feature appended under [Unreleased], derived from the feature's tiger/features/<id>/ artifacts and the semantic commit log) and at each release cut.
