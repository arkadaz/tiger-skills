# Full stack

One app codebase runs everywhere. Flutter draws the screens and Rust does everything else, the same Rust on every platform. The only other program is the backend, which is also Rust. The browser and the phone both talk to it under `/api/v1`.

The other skills hold here too. Each part is hexagonal (`tiger-hexagonal`). Settings come from the environment (`tiger-configuration`). Logs go to standard output (`tiger-logging`).

## The stack

For a new project. An existing project keeps the stack it has.

| Part | Built with |
|---|---|
| backend | Rust: axum, sqlx with Postgres, utoipa for the OpenAPI document |
| the app on web, Android, iOS, Windows, macOS and Linux | Flutter for the screens, Rust for every function, joined by flutter_rust_bridge |
| public pages that Google must find | Hugo with the PaperMod theme, written in Markdown |

Questions to ask before the first task, each with a recommended answer:

- how people sign in, and who may do what
- whether there are public pages, and in which languages
- the address the app is reached at

## Layout

```
Cargo.toml           the Rust workspace
crates/
  domain/            rules and types, no I/O. The backend and the app both use it.
  api/               the request and response types of /api/v1. Both sides use them.
  backend/           axum and sqlx: the HTTP adapter, the database adapter, main
  app_core/          what the app does: its use cases, and the client for /api/v1
app/
  rust/              the flutter_rust_bridge functions over app_core, and the types Dart sees
  lib/               screens, widgets and the theme. Dart only.
  lib/src/rust/      generated by flutter_rust_bridge. Never edited.
  web/ android/ ios/ windows/ macos/ linux/
site/                the public pages, in Markdown
docker/
  backend.Dockerfile
  web.Dockerfile     the public pages and the web build of the app, in one nginx image
  web.nginx.conf.template   nginx's config, filled in from the settings when it starts
openapi.yaml         written by the backend from its code
compose.yaml
.env.example         every setting with a harmless value. The real .env is never committed.
.gitattributes       line endings, and the code that is copied in, as below
```

- The Docker build context is the root of the repository, because the backend and the app share crates.
- `.gitattributes` holds exactly these lines:

```
* text=auto eol=lf
app/rust_builder/** linguist-vendored
app/android/** linguist-vendored
app/ios/** linguist-vendored
app/linux/** linguist-vendored
app/macos/** linguist-vendored
app/windows/** linguist-vendored
site/themes/** linguist-vendored
```

- The first line makes every checkout use LF, the line ending that flutter, the codegen and the backend's `openapi` write. Without it, on Windows, `flutter pub get` and every generated file show as changed when only line endings differ. A project that lacks it gets it in its own chore commit: add the file, then `git add --renormalize .`.
- The other lines mark code the project copied in and never writes: the bridge's build tool, the platform runners that `flutter create` writes, and the theme. The code map leaves them out; without these lines they are most of it. The bridge's generated files need no line, because they say they are generated.
- In the code map, a Dart call into the bridge, such as `renameNote  [app/lib/src/rust/api/notes.dart]  (generated)`, ends there. Its Rust side is the block that starts at `rename_note` in `app/rust/src/api/notes.rs`, which runs on through `app_core` to the HTTP call. The backend's side is the block that starts at the route, such as `PATCH /api/v1/notes/{noteId}`.

## The contract

- The types in `crates/api` are the contract. The backend and `app_core` both use them, so a renamed field breaks the build on both sides at once.
- The backend writes the same contract as `openapi.yaml` from those types, for anyone else who calls the API, and serves it at `GET /api/v1/openapi.json`. Every endpoint is in it, and nothing in it is gone (OWASP API9).
- A rule both sides need, such as what a valid id or title is, lives once in `domain`, as `NoteId::parse` and `NoteTitle::parse`. The backend's handlers and `app/rust` call it. Neither side keeps its own copy, not even one line of `Uuid::parse_str`.
- A task in `app_core` that calls an endpoint waits for the task that puts its types in `crates/api`. Everything else on the two sides shares no file and is built at the same time.

## Paths

```
GET    /api/v1/orders                       the list
POST   /api/v1/orders                       create one
GET    /api/v1/orders/{orderId}             one
PATCH  /api/v1/orders/{orderId}             change some of its fields
DELETE /api/v1/orders/{orderId}             delete it
GET    /api/v1/orders/{orderId}/lines       a list that belongs to one order
POST   /api/v1/orders/{orderId}/cancel      an action that is not create, change or delete
```

- Every endpoint starts with `/api/v1`. The health endpoints are the only ones outside it.
- A collection is a plural noun in lower case, words joined by `-`: `/api/v1/delivery-slots`, never `/api/v1/getDeliverySlot`.
- A verb appears only for an action, with POST, as the last part of the path.
- At most one level of nesting. Anything deeper is its own collection with a filter.
- No trailing slash and no file extension.

## Versions

- The major version is in the path: `v1` (Google AIP-185). Never a minor version such as `v1.2`, a date, or a version in a header.
- Only a breaking change makes `v2`. Adding an endpoint, an optional input or a field in a response is not breaking, and stays in `v1`. Clients ignore fields they do not know.
- Breaking: removing or renaming a field or an endpoint, changing a field's type or meaning, making an input required, changing a status code.
- An installed app cannot be made to update. `v1` keeps answering as long as the oldest app version still supported is out there. It sends the headers `Deprecation` (RFC 9745) and `Sunset` (RFC 8594) once its end date is set.
- A breaking change is always asked (`tiger-grill`: a public API other people depend on).

## Status codes

| Request | Success |
|---|---|
| GET a list or one | 200 |
| POST that creates | 201, the new record, and `Location: /api/v1/orders/ord_8f2k` |
| POST an action | 200 with the result, or 202 when it finishes later |
| PATCH | 200 and the whole record after the change |
| DELETE | 204 and no body |

| What went wrong | Status |
|---|---|
| the body is not JSON, a query parameter cannot be read, or the path is not valid text, such as `%FF` | 400 |
| not signed in, or the session expired | 401 |
| signed in, but this caller may not do this | 403 |
| no such record, an id in the path that is not in our format, or a record that belongs to someone else | 404 |
| it conflicts with what is stored: a duplicate, or the wrong state such as "already shipped" | 409 |
| the body is too large | 413 |
| the body is not `application/json` | 415 |
| it parsed, but a field is missing, unknown, of the wrong type, or breaks a rule | 422 |
| too many requests | 429, with `Retry-After` |
| our fault | 500 |
| a service it needs is down | 503 |

Never 200 with an error inside the body. axum's own `Json` extractor already answers 400, 415 and 422 in these cases. Its rejections are turned into the error body below too.

## The error body

Every 4xx and 5xx answer has the same shape, the problem details of RFC 9457, sent as `Content-Type: application/problem+json`:

```json
{
  "type": "https://example.com/problems/out-of-stock",
  "title": "Out of stock",
  "status": 409,
  "detail": "Only 2 of product p_42 are left, 3 were asked for.",
  "instance": "/api/v1/orders",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

- `type` names the kind of problem, and the app switches on it. Use `about:blank` when the status says it all.
- `title` is the same for every problem of that type. `detail` describes this one.
- A 422 lists every field that is wrong: `"errors": [{"detail": "must be an email address", "pointer": "#/email"}]`.
- `traceId` is the id in the log line for this request, so a user's screenshot leads to the log.
- A 500 says only "Internal error" and its `traceId`. The stack trace, the SQL and the error text go to the log, never to the response.
- One place builds it: one error type in the backend, with one `IntoResponse` that maps each domain error to its status and its type. A handler never writes its own error JSON.

## JSON

- Every body is a JSON object, never a bare list or value, so a field can be added later.
- Field names are camelCase, set once per type with `#[serde(rename_all = "camelCase")]`.
- Times are RFC 3339 in UTC: `"2026-11-11T09:30:00Z"`. A date alone is `"2026-11-11"`. Never a number of seconds, and never a local time without its offset.
- Money is a decimal string and a currency code: `{"amount": "19.99", "currency": "THB"}`. Never a float.
- Ids are strings, such as `"ord_8f2k"` or a UUID.
- A fixed set of values is a string: `"status": "SHIPPED"`, never `2`.
- The types in `crates/api` are not the domain types or the database rows. Only the fields they name go out, and only the fields they name are read. Request types carry `#[serde(deny_unknown_fields)]`, so an extra field such as `"role": "admin"` in a sign-up is refused with 422 (OWASP API3).
- serde's derive also reads a struct from a JSON list, by position, so `["Buy milk"]` would pass as `{"title": "Buy milk"}`. The backend has one JSON extractor of its own that refuses any body that is not an object with 422, then deserializes the type. It is used for every request type. Never a hand-written `Visitor` for each type.

## Lists

- Every list endpoint returns pages from its first version: `GET /api/v1/orders?limit=20&cursor=eyJpZCI6...`
- The answer is `{"items": [...], "nextCursor": "eyJpZCI6..."}`. `nextCursor` is `null` on the last page.
- The cursor is opaque. The client sends back what it was given and never builds one (Google AIP-158).
- `limit` has a default and a largest value, named in the spec, such as 20 and 100. A larger `limit` is cut to the largest.
- The order always ends on a unique field, as in `createdAt` then `id`, so no item is shown twice or skipped.
- A filter is a query parameter named after its field: `?status=SHIPPED`. Sorting is `?sort=-createdAt`.

## Safe to send twice

- GET, PUT and DELETE give the same result when they are sent twice. A DELETE of a record that is already gone answers 204 again, so a phone that sends it again after a lost answer sees no error.
- A POST that must not happen twice, such as placing an order or taking a payment, takes an `Idempotency-Key` header. The same key again returns the first answer and does nothing new (IETF draft `httpapi-idempotency-key-header`). A phone on a bad network sends things twice.

## Health

- `GET /livez` answers 200 while the process runs. It checks nothing outside the process, so a database outage does not restart every container.
- `GET /readyz` answers 200 when the service can serve, such as when its database answers, and 503 when it cannot.
- Both are outside `/api/v1`, need no sign-in, and put no detail in the body.

## Sign-in

- In the browser, the backend runs the sign-in. It runs the OAuth 2.0 code flow with PKCE (the `oauth2` crate) and sets the session in a cookie: `HttpOnly; Secure; SameSite=Lax; Path=/`. The app in the browser never holds a token.
- On a phone or desktop, the app's Rust runs the same flow (RFC 8252, OAuth 2.0 for Native Apps). Rust builds the address with PKCE. Dart opens it in the system browser with `flutter_web_auth_2` and hands back the address the sign-in returned to. Rust then trades the code for the tokens. Never a WebView inside the app.
- The refresh token is kept in Keychain or Keystore through `flutter_secure_storage`. Never in SharedPreferences or a file. Calls carry `Authorization: Bearer <token>`.
- The backend checks the cookie and the token in one place, for every request.
- A request that changes something is never a GET. A cookie request whose `Origin` header is not the app's own address, which is a setting, is refused with 403.

## OWASP API Security Top 10 (2023)

| Risk | The rule |
|---|---|
| API1 object level authorization | every id in a request is checked against the caller in the use case, and a record that is not theirs is 404 |
| API2 authentication | as under Sign-in. Sign-in, sign-up and password reset answer 429 when called too often |
| API3 object property level authorization | the types in `crates/api`, as under JSON |
| API4 unrestricted resource consumption | a largest page, a largest body, a timeout on every outgoing call. In `app_core` it is set on each request with `.timeout(Duration::from_secs(10))`, because reqwest has no client-wide timeout in the browser |
| API5 function level authorization | the backend checks the role for every endpoint. A hidden button is not a check |
| API6 sensitive business flows | a flow that can be abused at volume, such as sign-up or checkout, gets a limit per caller. The number is asked |
| API7 server-side request forgery | the backend never fetches a URL a user gave, unless its host is on a list in the settings |
| API8 security misconfiguration | no stack trace in a response, no CORS (one origin, as under Docker images), the headers below, debug off |
| API9 improper inventory management | every endpoint is in the contract, and an old version is listed with its sunset date |
| API10 unsafe consumption of APIs | what another API returns is checked like user input |

## The app: Flutter draws, Rust does

- Dart builds widgets and nothing else. A Dart function does one of three things: it builds a widget, calls a Rust function, or puts that function's answer on the screen with `setState`.
- Everything else is a Rust function: every rule, every check of what the user typed, every call to the backend, every conversion, every date and money format, and all state that outlives one screen.
- `app/` is made once with `flutter_rust_bridge_codegen create app`, which writes the Flutter app, `app/rust` and `flutter_rust_bridge.yaml`.
- `app/rust` is thin. Each function calls `app_core` and converts its answer into the types Dart sees. After a function changes, `flutter_rust_bridge_codegen generate` writes the Dart side into `lib/src/rust/` again, and nobody edits it.
- `app_core` also runs in the browser. Its traits return `impl Future` with no `Send` bound, because a future in the browser is not `Send`. It calls the backend with reqwest over rustls, so no image needs OpenSSL.
- Some things only the platform can do: open the system browser, use the secure store, the camera, a file picker or push. For those, the Dart function is passed into the Rust call as an argument (`impl Fn(String) -> DartFnFuture<String>`). Rust still decides, and Dart only carries the result back.
- A single answer comes back as a `Future`, shown with `FutureBuilder`. A value that keeps changing, such as progress or live results, comes from Rust as a stream (`StreamSink`), shown with `StreamBuilder`.
- A Rust function that fails returns `Err(Problem)`, and Dart receives it as an exception of that type. Rust writes what the screen shows: `message`, and for a 422, `fields`, the reason for each field, taken from the backend's `errors`. The screen puts each reason under its field and shows `message` otherwise. Never the backend's `title`: for `about:blank` it is only the status, such as "Unprocessable Entity".
- `app_core` accepts only the status the endpoint promises on success, such as 201 for a create and 204 for a delete. Any other answer, a 200 from a proxy page included, is a `Problem`.
- Every screen that loads data shows four states: loading, empty, failed, and loaded. They are leaves of the decision tree.
- A dialog has a leaf for each of its buttons, and one for closing it without a choice (Escape, a tap outside, the back button), which does what Cancel does.
- A dialog that sends a request cannot be left while the request is on its way: every button is off, and `PopScope(canPop: !saving)` inside the dialog holds it open, because a tap outside and Escape both go through `Navigator.maybePop`. It closes when the answer comes. Not `barrierDismissible: false`: that is fixed when the dialog opens and would also stop a tap outside from cancelling before Save. Otherwise the service saves what the screen never shows.
- A button repeated on every row is named for its row, so a screen reader and the browser check can tell the rows apart: `IconButton(tooltip: 'Delete ${note.title}', ...)`, or `Text('Delete', semanticsLabel: 'Delete ${note.title}')` on a text button.
- A `Card` merges all its texts into one node, so its title alone cannot be found. Build it as `Card(semanticContainer: false, ...)`. A `Semantics(explicitChildNodes: true)` around the card does not stop the merge.
- Anything used twice is one widget in `lib/widgets/`. Buttons, inputs, cards and dialogs come from one UI package, `shadcn_ui` or Material 3, and are never built by hand. Colors, corners, spacing and dark mode live in `lib/theme.dart`.
- Fonts ship with the app, one for every script it shows, such as Thai, so text never waits for a font server.
- The backend's address: on the web it is the page's own origin, read in Rust. On every other platform it is given at build time in `API_BASE` and read with `env!("API_BASE")`, so a build without it fails. `app/rust` builds the one API client from it the first time a function needs it, keeps it in a `OnceLock`, and hands it to `app_core`.

The Rust that a screen calls, in `app/rust/src/api/notes.rs`:

```rust
static CLIENT: OnceLock<ApiClient> = OnceLock::new();

pub async fn list_notes() -> Result<NotePage, Problem> {
    let page = app_core::notes::list(client()).await?;
    Ok(NotePage::from(page))
}

pub async fn add_note(title: String) -> Result<Note, Problem> {
    let note = app_core::notes::add(client(), &title).await?;
    Ok(Note::from(note))
}

fn client() -> &'static ApiClient {
    CLIENT.get_or_init(|| ApiClient::new(settings::api_base()))
}
```

The screen, in Dart:

```dart
class NotesScreen extends StatefulWidget {
  const NotesScreen({super.key});

  @override
  State<NotesScreen> createState() => NotesScreenState();
}

class NotesScreenState extends State<NotesScreen> {
  final title = TextEditingController();
  Future<NotePage> notes = listNotes();
  Problem? refused;

  Future<void> add() async {
    try {
      await addNote(title: title.text);
    } on Problem catch (problem) {
      setState(() => refused = problem);
      return;
    }
    title.clear();
    setState(() {
      refused = null;
      notes = listNotes();
    });
  }

  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        TextField(
          controller: title,
          decoration: InputDecoration(
            labelText: 'New note',
            errorText: refused?.fields['title'] ?? refused?.message,
          ),
        ),
        FilledButton(onPressed: add, child: const Text('Add')),
        FutureBuilder(
          future: notes,
          builder: (context, result) {
            if (result.connectionState != ConnectionState.done) return const Text('Loading…');
            if (result.error case Problem problem) return Text(problem.message);
            final items = result.data!.items;
            if (items.isEmpty) return const Text('No notes yet.');
            return Column(children: [for (final note in items) NoteCard(note: note)]);
          },
        ),
      ],
    );
  }
}
```

## Public pages and SEO

The app sits behind sign-in, and Google never sees it. The pages Google must find are separate, such as the landing page, the pricing and the blog.

- They are Markdown files in `site/`, built by Hugo into plain HTML. Their text is in the page without JavaScript.
- The theme is PaperMod, copied into `site/themes/` at a commit that builds with the pinned Hugo. It writes the tags below from each page's front matter and `hugo.toml`, the share image from `params.images`, so nobody writes HTML. Every build runs with `--panicOnWarning`, so a theme that falls behind Hugo stops the build instead of quietly dropping tags.
- They are served at `/`, and the app at `/app/`. The app's answers carry `X-Robots-Tag: noindex`. `robots.txt` keeps out `/app/` and `/api/`.
- Each page has its own `<title>`, `<meta name="description">` and canonical URL. It has Open Graph tags (title, description, image), so a shared link shows a preview, and JSON-LD: PaperMod writes an Organization for the home page and an article for each other page. A page that needs another type, such as a Product, is a question for the user.
- Hugo writes `sitemap.xml`, and `robots.txt` from `layouts/robots.txt` with `enableRobotsTXT = true`. Kinds of page the site does not use are turned off with `disableKinds`, such as `["taxonomy", "term", "RSS"]`, so the sitemap lists only real pages. A page in two languages links each version to the other with `hreflang`.
- The pages pass Google's Core Web Vitals: the main content within 2.5 seconds, an answer to a tap within 200 milliseconds, and a layout shift below 0.1.
- A page that moved answers 301, from a line in the nginx config: `location = /old-page/ { return 301 /new-page/; }`. Hugo's `aliases` make a page that redirects with a 200, not a 301. A missing page answers a real 404.
- Public pages filled from the database, such as products or listings, are a question for the user. They cannot be static files.

## Docker images

Two images: `backend`, and `web` for everything the browser loads. The backend image runs the same on your machine and in production. Only its settings differ. The web image is built once for each public address, because the public pages carry it in their links.

```dockerfile
FROM lukemathwalker/cargo-chef:0.1.78-rust-1.99.1-slim-bookworm AS chef
WORKDIR /src

FROM chef AS plan
COPY . .
RUN cargo chef prepare --recipe-path recipe.json

FROM chef AS build
COPY --from=plan /src/recipe.json recipe.json
RUN cargo chef cook --release --recipe-path recipe.json
COPY . .
ENV SQLX_OFFLINE=true
RUN cargo build --release --locked -p backend

FROM gcr.io/distroless/cc-debian12:nonroot
COPY --from=build /src/target/release/backend /backend
EXPOSE 8000
ENTRYPOINT ["/backend"]
CMD ["serve"]
```

- The backend is one binary with four subcommands. `serve` runs the API. `migrate` runs the sqlx migrations, which are built into it. `healthcheck` asks `/readyz` and exits 0 or 1. The run image has no shell, so this is how compose checks it. `openapi` prints the contract.
- `serve` listens on `0.0.0.0`, on the port in the setting `PORT`, default 8000. Some platforms set `PORT` themselves, so it is never a constant in the code.
- cargo-chef builds the dependencies in their own layer, so a code change does not rebuild them. `--locked` builds from `Cargo.lock`.
- sqlx's checked queries (`query!`, `query_as!`) need a database at build time. Run `cargo sqlx prepare --workspace` and commit `.sqlx/`, so the image builds with `ENV SQLX_OFFLINE=true` and no database.
- `serve` stops cleanly on SIGTERM with `axum::serve(...).with_graceful_shutdown(...)`. It stops taking requests, finishes the ones it has, closes the pool and exits within 10 seconds, Docker's default.

The `web` image:

- `SITE_BASE_URL` is the public address. Hugo writes it into every canonical link, the sitemap and the Open Graph tags.
- No Flutter image is published for each version, so the SDK is cloned at the project's Flutter version.
- The web build of flutter_rust_bridge needs a nightly Rust with `rust-src` and the `wasm32-unknown-unknown` target. It is pinned to a date and named with `--wasm-pack-rustup-toolchain`, because `build-web` otherwise asks for a toolchain called plain `nightly`.
- `wasm-bindgen-cli` is the exact version of `wasm-bindgen` in `app/rust/Cargo.lock`.
- `--no-web-resources-cdn` puts everything in the image, so the app downloads nothing from Google's servers.

`docker/web.nginx.conf.template`:

```nginx
server {
  listen 8080;
  root /usr/share/nginx/html;
  add_header X-Content-Type-Options "nosniff" always;
  add_header Referrer-Policy "strict-origin-when-cross-origin" always;
  add_header Content-Security-Policy "frame-ancestors 'none'" always;

  location /api/ {
    proxy_pass ${BACKEND_ADDRESS};
    proxy_connect_timeout 5s;
    error_page 502 504 = @backend_down;
  }

  location @backend_down {
    default_type application/problem+json;
    return 503 '{"type":"about:blank","title":"Service Unavailable","status":503,"detail":"The service is unavailable. Try again later.","instance":"$request_uri","traceId":"$request_id"}';
  }

  location /app/ {
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Content-Security-Policy "frame-ancestors 'none'" always;
    add_header Cross-Origin-Opener-Policy "same-origin" always;
    add_header Cross-Origin-Embedder-Policy "require-corp" always;
    add_header X-Robots-Tag "noindex" always;
    try_files $uri $uri/ /app/index.html;
  }

  location / { try_files $uri $uri/ =404; }
}
```

- When nginx starts, it fills `${BACKEND_ADDRESS}` from the setting of that name and leaves nginx's own `$uri` alone. Compose sets it to `http://backend:8000`. Production sets the backend's real address.
- When the backend cannot be reached, nginx answers a 503 with the same problem body the backend writes, so the app says the service is unavailable, not that the reply was unreadable. `proxy_connect_timeout 5s` makes that answer come before the app gives up at 10 seconds (API4 above); nginx's default would wait about 40 seconds for a stopped container. The backend's own answers, its errors included, pass through unchanged.
- The two cross-origin headers are only on `/app/`. They let the app's Rust run on several threads in the browser. The public pages stay free to embed videos and images from elsewhere.
- nginx drops the headers of `server` in a `location` that sets its own, so `/app/` repeats them.
- The browser reaches the backend only through `/api/` on the same address, so there is no CORS.

For every image:

- Pinned to an exact version. Never `latest` and never a bare name.
- Runs as a user that is not root.
- `.dockerignore` keeps out `.git`, `target`, `app/build`, `.dart_tool`, `site/public`, `site/resources`, `.env` and test reports.
- Logs go to standard output. Never to a file inside the container.
- No secret in the image: not in `ENV`, not in `ARG` (build arguments stay in the image's history), not in a copied file. Secrets arrive when the container starts.

## compose.yaml

```yaml
services:
  web:
    build:
      context: .
      dockerfile: docker/web.Dockerfile
      args:
        SITE_BASE_URL: http://localhost:${WEB_PORT:-8080}/
    environment:
      BACKEND_ADDRESS: http://backend:8000
    ports:
      - "127.0.0.1:${WEB_PORT:-8080}:8080"
    depends_on:
      backend:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://127.0.0.1:8080/app/"]
      interval: 5s
      retries: 5
  backend:
    build:
      context: .
      dockerfile: docker/backend.Dockerfile
    environment:
      DATABASE_URL: postgresql://app:${DATABASE_PASSWORD:?set DATABASE_PASSWORD in .env}@db:5432/app
    depends_on:
      migrate:
        condition: service_completed_successfully
    healthcheck:
      test: ["CMD", "/backend", "healthcheck"]
      interval: 5s
      retries: 5
      start_period: 10s
  migrate:
    build:
      context: .
      dockerfile: docker/backend.Dockerfile
    command: ["migrate"]
    environment:
      DATABASE_URL: postgresql://app:${DATABASE_PASSWORD:?set DATABASE_PASSWORD in .env}@db:5432/app
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:17.2
    environment:
      POSTGRES_USER: app
      POSTGRES_DB: app
      POSTGRES_PASSWORD: ${DATABASE_PASSWORD:?set DATABASE_PASSWORD in .env}
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "app"]
      interval: 5s
      retries: 10
volumes:
  db-data:
```

- Compose is for running on your own machine, and for the end-to-end tests. It never deploys anything.
- Production runs the same two images, pushed to a registry. The platform and the managed database are created with Terraform (`tiger-terraform`). Its secrets come from the secret store, and `migrate` runs there as a one-off job before a new backend version starts. The `db` service and the `.env` file exist only on your machine.
- The file is `compose.yaml`, with no `version:` line.
- `docker compose up --build --wait` starts everything on a machine that has only Docker and a `.env` copied from `.env.example`.
- Only `web` publishes a port, and only on `127.0.0.1`, so no other machine on the network reaches it. `WEB_PORT` picks the port, 8080 unless set, so two projects can run side by side. The backend and the database are reached by service name, inside compose's network.
- `.env` only fills the `${...}` in this file. A setting reaches a container only when its service lists it under `environment:`.
- A health check asks `127.0.0.1`, not `localhost`, which can mean IPv6, where nginx is not listening.
- Every long-running service has a health check. `depends_on` waits for `service_healthy`, and for `service_completed_successfully` on the one-off `migrate`. A bare `depends_on: [db]` waits for nothing.
- A required setting is written `${NAME:?set NAME in .env}`, so compose stops and names it when it is missing.
- Data lives in a named volume. `docker compose down -v` deletes it, so it is never run without asking.
- The phone and desktop builds are not images. They are built with `flutter build apk`, `ipa`, `windows`, `macos` or `linux`, and an iOS build needs a Mac.

The rows use port 8080. When `.env` sets `WEB_PORT`, every command that reaches the stack, the browser check included, uses that port instead: `port=$(sed -n 's/^WEB_PORT=//p' .env | tr -d '\r')`, then `http://127.0.0.1:${port:-8080}`. A command written into a plan is never given a fixed port.

- The web build is checked with Playwright in a real browser, against `web` from compose, the way users get it. Not `flutter drive`: it serves the app from its own address, where `/api/` is not the backend. Flutter draws on a canvas, so:
  - First run `document.querySelector('flt-semantics-placeholder').click()` in the page to turn on its accessibility tree.
  - Search only inside that tree: `screen = page.locator('flt-semantics-host')`, then `screen.get_by_role('textbox')`, `screen.get_by_role('button', name='Add')`, `screen.get_by_text('Buy milk', exact=True)`. Flutter also copies every message it announces, such as a snackbar, into a hidden element outside the tree, so a search of the whole page now and then finds the text twice and the check fails at random.
  - Click a text field before `fill`. Flutter ignores `fill` on a field that has no focus, now and then, so a check that skips the click passes most runs and fails some.
  - The check's own calls to the API, to set up its data, carry a timeout: `urlopen(request, timeout=10)`. A check that hangs proves nothing.
  - In the browser, Flutter often spends the first Escape on focus, leaving the text field or moving into the dialog, and closes the dialog on the second. `autofocus` does not change that. A check that closes a dialog with Escape presses it until the dialog is gone, at most twice, then checks what Escape must do: nothing was sent and the old value stays. A check that expects Escape to leave the dialog open presses it twice, so a press spent on focus does not pass for a refusal.
- On Windows, macOS, Linux or an emulator, the screens are checked with `flutter test integration_test -d <device>`, against the compose stack.
- The rules are tested in Rust. Domain tests run in `crates/domain`, and use case tests run in `app_core` against an in-memory version of the API client.
- The list "Input from outside" in `tiger-verification` runs against every endpoint that takes input.
- When the project has them: `hadolint` on each Dockerfile, `trivy image` on each image, and Lighthouse on the public pages.
